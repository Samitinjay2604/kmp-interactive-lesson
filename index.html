    Start here · 3 min

    Find a needle without re-reading the haystack

    When you press Ctrl+F, scan a genome for a gene, or filter server logs for an error code, the program is solving one problem: find every place a short pattern occurs in a long text.

    The obvious method works, but when a match fails it goes back and re-reads characters it has already seen. The Knuth–Morris–Pratt algorithm (KMP, 1977) avoids that with one idea. When a match fails, the pattern itself tells you how far you can safely slide it, so the reading position in the text never moves backward.

    By the end of this lesson you will be able to…
    1. explain why naive search can take O(n·m) time;
    2. compute the LPS table of any pattern by hand;
    3. trace KMP on an example and predict every “fallback”;
    4. implement KMP in Python or Java and justify its O(n + m) time and O(m) space;
    5. reuse the LPS idea to solve new problems.

    Step 1 · 5 min

    The obvious way, and where it wastes work

    Naive search places the pattern at every start position s and compares character by character, left to right. At the first mismatch it gives up, slides the pattern one place right, and starts again from pattern[0].

    Step through it below. Watch the reads row, which counts how many times each text character has been compared.

    What to notice

    Pick “Naive's nightmare”. After matching AAA and failing on B, naive slides by one and compares those same As again. In the worst case every one of the n − m + 1 positions costs up to m comparisons, so the total is O(n·m). For a 1,000,000-character text and a 1,000-character pattern, that is about a billion comparisons.

    Checkpoint
    Step 2 · 5 min

    The key insight: a mismatch is information

    Suppose we have matched j characters and then hit a mismatch. We now know the last j text characters exactly: they are pattern[0..j-1]. So the question “where could the next match start?” can be answered from the pattern alone, without looking at the text again.

    1. We matched ABACABA (7 characters), then text[7] = C did not equal pattern[7] = B.
    2. Sliding by 1, 2 or 3 cannot work. For the pattern to line up there, a longer prefix of ABACABA would have to equal a suffix of it, and none does.
    3. ABACABA starts and ends with ABA, so we slide the pattern until its first ABA sits on the text's last ABA. Those 3 characters are already known to match. We continue at text[7] vs pattern[3], and the text pointer never moved back.
    Definition: border

    A proper prefix of a string is a prefix that is not the whole string. A border is a string that is both a proper prefix and a suffix. ABACABA has borders A and ABA. Its longest border, ABA (length 3), gives the smallest slide that could still produce a match. A smaller slide is impossible, and a bigger one might skip a match.

    Type any string. The table compares every proper prefix with the suffix of the same length.

    Step 3 · 8 min

    Precompute every border: the LPS table

    A mismatch can happen after any number of matched characters, so we store the longest border of every prefix of the pattern:

    lps[i] = length of the Longest proper Prefix of pattern[0..i] that is also a Suffix of it.

    Example for ABABAC: prefix ABABA has longest border ABA, so lps[4] = 3. The full table is [0, 0, 1, 2, 3, 0].

    Checking every prefix against every suffix would be slow. Instead, the pattern searches itself. We keep length, the border we are trying to extend, and look at pattern[i]:

    1. Equal (pattern[i] == pattern[length]): the border grows by one. Set lps[i] = length + 1 and move to the next i.
    2. Different, and length > 0: try the next-shorter border, length = lps[length − 1]. Don't move i; compare again.
    3. Different, and length == 0: no border ends here. Set lps[i] = 0 and move on.
    Why lps[length − 1] in rule 2?

    A border of a border is itself a border. The current border is pattern[0..length−1], and its longest border is lps[length−1], which is exactly the next-longest border to try. We never search for it; we just read it from the table.

    Activity: fill in the LPS table yourself

    For each index, find the longest border of the prefix ending there. Use the border explorer or the rules above. Aim for 2 patterns correct in a row.

    Step 4 · 8 min

    Searching with the table

    Now scan the text once, left to right. i is the text position and j is how many pattern characters currently match. Compare text[i] with pattern[j]:

    1. Equal: j += 1, then move to the next text character.
    2. Different, and j > 0: fall back with j = lps[j − 1] and compare the same text[i] again. The text never rewinds.
    3. Different, and j == 0: nothing to reuse, so move to the next text character.
    4. j == m: a full match ends at i, starting at i − m + 1. Record it and set j = lps[m − 1] so overlapping matches are still found.

    Step 6 · 4 min
    
  
    Why it is O(n + m), even with a loop inside a loop
    
  
    
    
    The search has a while inside a for, which looks like it could be O(n·m). It isn't. Think of j as a bank balance:
    
  
    
  
      
    
    1. j starts at 0 and never goes below 0.
      2. 
    
    2. It goes up by at most 1 per text character (j += 1), so over the whole run it goes up at most n times.
      3. 
    
    3. Every fallback makes it go down by at least 1, because lps[j−1] < j.
      4. 
    
    4. You can't take out more than you put in, so there are at most n fallbacks in total. Each character has one final comparison, plus its share of those fallbacks: at most 2n comparisons.
      5. 
  
    
  
    The same argument with length gives at most 2m comparisons for build_lps. Total time is O(n + m) in the worst case, not just on average.
    

  
    See the balance
    
  
    This is j after every step of the run in the Step 4 visualizer. It updates when you change that input. Each climb is at most one step at a time; each drop is a fallback.
    
  
    

  
    Space
    
  
    KMP stores the lps array, so it uses O(m) extra space, plus the output list. Naive search uses O(1) extra space. KMP spends a little memory to guarantee linear time.

    Step 7 · 2 min
    
  
    Edge cases worth testing
    
  
    Click Try it to load a case into the Step 4 visualizer.
    
  
    
    
    Overlapping matches
    ABABABAB / ABAB → [0, 2, 4]. Setting j = lps[m−1] after a match (not 0) is what finds 2 and 4.
    
    
    Pattern longer than text
    ABC / ABCD: j can never reach m, so the result is [] with no special case needed.
    
    
    All characters equal
    AAAAAA / AAA: lps = [0,1,2], and it matches at every index 0–3.
    
    
    Pattern equals text
    KMP / KMP → [0]. The match is found at the last character.
    
    
    Empty pattern
    The empty string occurs at every position, so our code returns [0, 1, …, n], which agrees with Python's "abc".find("") == 0. Libraries differ here, so decide the rule explicitly. (The visualizer requires a non-empty pattern.)
    
    
    Case and alphabet
    Comparisons are exact: a ≠ A. Normalise case first if needed. KMP never depends on alphabet size, so it works the same for DNA, bytes or Unicode.
